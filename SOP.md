# SOP: Инструмент агента «Создать тикет» (`create_ticket`)

Стандартная операционная процедура для интеграции внешнего инструмента
(тикеты поддержки) в LLM-агента на LangGraph. Написана для разработчика,
операционного аналитика и менеджера: все шаги можно выполнить, не спрашивая
автора, что именно и зачем делать.

- Версия документа: 1.1 (14.09.2026)
- Ответственный за документ: владелец репозитория DZ_7_case1
- Связанные файлы: `agent.py`, `ticket_server.py`, `tool_schema.json`,
  `.env.example`, `requirements.txt`

---

## 1. Область применения

**Что покрывает:** сценарии, в которых запрос пользователя требует передачи
специалисту — классификатор вернул `risk="medium"` (жалоба с требованием,
неоднократно нерешённая проблема, жалоба на сотрудника). Агент при этом уже
сформулировал и проверил ответ по базе знаний; тикет фиксирует обращение
во внешней тикет-системе, и прогон завершается исходом `escalated`
(`ticket_created`) с id тикета в ответе.

**Кто использует:**

- разработчик, повторяющий или расширяющий интеграцию;
- операционный аналитик, проверяющий, что агент корректно создаёт тикеты;
- менеджер, принимающий решение об эскалации при сбое тикет-сервиса.

**Что НЕ покрывает:** тикеты по `risk="high"` (также эскалация, но без
создания тикета — сразу оператору), управление тикетами после создания
(статусы, дубли, закрытие), другие внешние системы.

## 2. Предрасчётные условия

До первого вызова должны быть готовы:

| # | Что | Как проверить | Критерий готовности |
|---|-----|---------------|---------------------|
| 1 | Python 3.13 | `python3.13 --version` | версия выведена |
| 2 | Зависимости в venv | `python3.13 -m venv .venv && .venv/bin/pip install -r requirements.txt` | пакеты `openai`, `python-dotenv`, `qdrant-client`, `jsonschema`, `langgraph`, `grandalf` установлены |
| 3 | Файл `.env` (скопирован из `.env.example`) | `cp .env.example .env` | файл существует, `.env` в `.gitignore` |
| 4 | LLM-сервер: LM Studio (порт 1234) с чат- и embedding-моделями | `curl -s http://localhost:1234/v1/models` | список моделей; `CHEAP_MODEL`/`ADVANCED_MODEL` из `.env` в списке |
| 5 | Тикет-сервис запущен | `.venv/bin/python ticket_server.py`, затем `curl -s http://127.0.0.1:8766/health` | `{"status": "ok", ...}` |
| 6 | Права на запись `data/` (для `tickets.json`) | `touch data/.t && rm data/.t` | без ошибок |

Ключи для тикет-сервиса **не нужен**: сервис локальный, без авторизации.

## 3. Пошаговая процедура

Путь одного запроса, попадающего в ветку тикета, от начала до финального
ответа. Метки: **[LLM]** — запрос к модели, **[API]** — HTTP-вызов к
тикет-сервису, **[Валидация]** — проверка схемы.

1. **Получен вопрос пользователя** (CLI: `agent.py "<вопрос>"` или интерактив).
2. **[LLM]** Классификация (CHEAP-модель): категория, риск, сложность, язык.
   `risk="high"` — эскалация без тикета; `risk="medium"` — ветка тикета
   дальше по сценарию.
3. Векторный поиск по БЗ (Qdrant, top-3), проверка релевантности,
   генерация ответа и проверки (`check_answer` + LLM-валидатор) — как в
   основном сценарии; тикет создаётся только после того, как ответ прошёл
   обе проверки.
4. **[LLM]** Узел `tool_create_ticket` просит CHEAP-модель сформировать
   вызов: «верни один JSON `{"name": "create_ticket", "arguments": {...}}`».
5. **[Валидация]** `validate_tool_call()` по `tool_schema.json`
   (draft-07, единый источник — тот же файл передаётся LLM в `tools=[...]`):
   - имя функции = `create_ticket`;
   - `title` — строка 5–200 символов;
   - `priority` — `low | normal | high | critical` (enum);
   - `body` — строка 10–2000 символов;
   - `additionalProperties: false` — лишние поля запрещены.
    - **Ошибки есть** → текст ошибок возвращается модели, повтор вызова,
      максимум `MAX_TOOL_STEPS` (4) попыток всего (`MAX_VALIDATION_RETRIES`
      к инструменту не относится — он ограничивает перегенерацию ответа);
      при исчерпании — эскалация
      `tool_error:create_ticket: невалидные аргументы…`.
   - **Ошибок нет** → шаг 6.
6. **[API]** `POST {TICKET_API_URL}/tickets` с телом `{title, priority, body}`,
   таймаут `TICKET_TIMEOUT_SECONDS` (5 с). Сетевой таймаут/сбой — 2 ретрая
   с backoff 1 с / 2 с (счётчик `tool_retries`). HTTP 4xx/5xx ретраить не —
   сразу ошибка. Ответ без `ticket_id` — ошибка.
7. **Результат:** `{"ticket_id": "TKT-…", "status": "open"}` сохраняется в
   состоянии графа; тикет-сервис дописывает запись в `data/tickets.json`
   (атомарно, `.tmp` + `os.replace`). Узел `save` кладёт Q&A в память,
   терминал `finish` выдаёт исход `escalated` (`ticket_created`), и id
   тикета присутствует в сообщении пользователю.
   **Сбой сервиса после ретраев** → `ticket` считается несозданным,
   прогон завершается `escalated` с причиной `tool_error:create_ticket: …`,
   падение (traceback) исключено.

## 4. Критерии успеха

Запрос считается отработавшим корректно, если выполняются **все** условия:

1. Процесс завершился с кодом 0; в ответе `[escalated]` с причиной
   `ticket_created` и строкой «тикет TKT-…».
2. В `data/tickets.json` появилась ровно одна новая запись с полями
   `ticket_id`, `status=open`, `title`, `priority` (из enum), `body`.
3. В логе `logs/runs.jsonl` запись прогона: `outcome=escalated`,
   `escalated_reason=ticket_created`, `tool_calls=1`, `model_used`
   заполнен.
4. При невалидных аргументах модели (самодемонстрация: режим selftest
   `tool_bad`) — в логе warning «невалидные аргументы (попытка 1)»,
   повтор, тикет создан валидными аргументами.
5. `agent.py --selftest` завершается строкой
   `SELF-TEST: все проверки пройдены.` (12 проверок, проверка 10 —
   тикет-инструмент: невалидные аргументы → повтор; сервис down →
   `tool_error` + эскалация без падения; HTTP 5xx → без ретраев).

Эталонные запросы для живого прогона (регрессия):

- «Возврат денег по заказу 4821 тянется две недели, менеджер меня игнорирует,
  готовлю претензию» → `risk=medium` → тикет `high`-приоритета.
- «Как вернуть товар, если он не подошёл?» → `risk=low` → тикет НЕ создаётся.
- «Я хочу на вас подать в суд и причинить вред себе.» → `risk=high` →
  эскалация `high_risk`, тикет НЕ создаётся.

## 5. Инцидент-менеджмент

| Тип ошибки (симптом в логах) | Действие оператора/агента | Эскалация (кому, когда) |
|---|---|---|
| Тикет-сервис: тайм-аут/сети, `tool_error:create_ticket: сетевая ошибка: …` | 1) Авто-ретраи 1 с/2 с уже сделаны кодом. 2) Проверить, запущен ли `ticket_server.py`: `curl -s http://127.0.0.1:8766/health`. 3) Проверить `TICKET_API_URL`/`TICKET_TIMEOUT_SECONDS` в `.env`. 4) Перезапустить сервис и повторить запрос. | Если сбой > 15 мин — разработчику; пользователю агент уже передал запрос оператору (эскалация выполнена). |
| Тикет-сервис: `HTTP 5xx` | Не ретраится (SOP): прогон завершён `tool_error:create_ticket: HTTP …`. Проверить лог тикет-сервиса и доступность `data/tickets.json` (права, место на диске). | Повторяющийся сбой > 1 дня — разработчику с прикладом строк лога. |
| Тикет-сервис: ответ без `ticket_id` (битый JSON) | Проверить целостность `ticket_server.py` (git status), перезапустить сервис. | Разработчику, который правил сервис. |
| Валидационная: `невалидные аргументы (попытка N)` (≥ `MAX_TOOL_STEPS`) | 1) Прочитать список ошибок в логе — обычно модель нарушает enum `priority` (`urgent` вместо `high`) или длину `title`/`body`. 2) Повторить запрос. 3) Если повторяется на разных вопросах — модель слаба для tool calling. | При систематических ошибках — сменить `CHEAP_MODEL` на более сильную и прогнать регрессию из раздела 4. |
| LLM не отвечает: `APITimeoutError`/`APIConnectionError`, `step_error:classify` | 1) Авто-ретраи 0.5 с/1.5 с уже сделаны. 2) Проверить LM Studio (Local Server, порт 1234) и загруженность модели. 3) Проверить `LLM_BASE_URL`/`LLM_API_KEY` в `.env`. 4) Повторить запрос. | Если недоступность > 10 мин — разработчику LLM-инфраструктуры. |
| Бюджет: `budget_exceeded` | Нормальная работа предохранителя: ретраи валидации/тикета сожрали `MAX_LLM_CALLS_PER_RUN` (6). Проверить `--report` — если чаще 1 на 20 прогонов, поднять лимит или укрепить модель. | Не требуется, если алерт `[АЛЕРТ]` не постоянный. |
| `SELF-TEST` упал на проверке 10 | Сверить `tool_schema.json` с `agent.py` (единый источник); проверить, что `ticket_server.py` не правили «в лоб». | Разработчику, который правил схему/сервис. |

## 6. Обновление и поддержка

**Когда обновлять инструмент:**

- изменился контракт тикет-системы (поля, статусы, endpoints) — сначала
  `tool_schema.json` + `ticket_server.py`, потом узел `node_tool_create_ticket`
  в `agent.py`, потом регрессия;
- добавляется новый аргумент (например, `due_date`) — сначала схема, потом
  код, потом selftest;
- меняется приоритизация — только enum в `tool_schema.json` + промпт
  `TICKET_SYSTEM_PROMPT`;
- меняется LLM-бэкенд (модели/провайдер) — только `.env`.

**Регрессионная проверка (обязательна перед каждым изменением):**

1. `.venv/bin/python agent.py --selftest` — все 12 проверок `[OK]`
   (проверка 10 покрывает in-process мок тикет-сервиса: валидные и
   невалидные аргументы, сервис down, HTTP 5xx без ретраев);
2. живой прогон эталонного набора из раздела 4 (нужны LM Studio,
   `docker compose up -d` и `ticket_server.py`);
3. сверить `tool_schema.json` с онлайн-валидатором JSON Schema (draft-07):
   валидный инстанс `{"title": "Возврат по заказу 4821", "priority": "high",
   "body": "Клиент ждёт возврата, срок нарушен."}` обязан пройти,
   `{"title": "x", "priority": "urgent", "extra": 1}` — обязан показать
   ошибки по `minLength`, `enum`, `additionalProperties`.

**Порядок внесения изменений:** правка → `--selftest` → живой прогон →
обновить этот SOP (раздел 3 и таблицу инцидентов, если изменилось
поведение) → коммит. Номер версии документа в шапке bump-ится при каждом
изменении.

**Известные особенности:**

- Тикет-сервис — мок на stdlib: нет авторизации, очередь и SLA; данные —
  один файл `data/tickets.json` (append). Для «боевой» замены достаточно
  реализовать тот же контракт `POST /tickets` → `{"ticket_id", "status"}`.
- Тикет создаётся **только** при `risk="medium"` и только после успешной
  валидации ответа; `risk="high"` эскалируется раньше (без тикета) —
  намеренное решение плана.
- `data/tickets.json` отслеживается в git намеренно (часть сдачи): перед
  коммитом смотреть diff; selftest пишет только в tmp-каталог.
